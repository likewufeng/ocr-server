**部署方式**

生产环境：

```bash
docker compose up -d --build
```

本地 Docker 热更新开发：

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

双实例 CPU 生产部署：

```bash
docker compose -f docker-compose.scale.yml up -d --build
```

**服务管理**

Docker 对外端口由 `.env` 中的 `OCR_HOST_PORT` 控制，默认值为 `18081`：

```dotenv
OCR_HOST_PORT=18081
```

修改后需要使用后文的 `up -d --force-recreate` 重新创建容器，访问地址相应变为
`http://127.0.0.1:<OCR_HOST_PORT>`。容器内部端口保持 `8000`，无需修改。

当前双实例生产服务使用以下命令：

```bash
# 临时停止（保留容器）
docker compose -f docker-compose.scale.yml stop

# 启动已停止的容器
docker compose -f docker-compose.scale.yml start

# 重启服务（不重新构建镜像）
docker compose -f docker-compose.scale.yml restart

# 完全停止并删除容器和网络，不会删除 data 目录
docker compose -f docker-compose.scale.yml down

# 查看服务状态
docker compose -f docker-compose.scale.yml ps

# 持续查看最近 200 行日志
docker compose -f docker-compose.scale.yml logs -f --tail=200
```

单实例生产服务将上述命令中的
`docker compose -f docker-compose.scale.yml` 替换为 `docker compose`。本地 Docker
热更新开发服务则替换为：

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml
```

`restart` 只重启现有容器，不会读取新的 Compose 环境配置，也不会重新构建镜像。
修改 `.env` 或 Compose 配置后执行：

```bash
docker compose -f docker-compose.scale.yml up -d --force-recreate
```

修改 `Dockerfile`、依赖文件或生产镜像中的代码后执行：

```bash
docker compose -f docker-compose.scale.yml up -d --build
```

该模式由 Nginx 通过宿主机 `OCR_HOST_PORT`（默认 `18081`）端口按最少连接数分发请求（容器内仍监听
`8000`）。两个 OCR 实例各自保持
`OCR_MAX_CONCURRENT_REQUESTS=1`，默认各使用 4 个 CPU 线程，可通过
`OCR_SCALE_CPU_THREADS` 调整。建议服务器至少有 8 个可用逻辑核；核数更多时也应
先通过压测再提高线程数，避免两个实例争抢 CPU。

单实例监控地址为 `http://127.0.0.1:18081/metrics/json`，Prometheus 文本地址为
`http://127.0.0.1:18081/metrics`。双实例模式需要分别采集 `ocr-1:8000/metrics` 和
`ocr-2:8000/metrics`；宿主机排查端口分别为 `127.0.0.1:8001`、
`127.0.0.1:8002`。Nginx 会屏蔽 `18081/metrics`，避免误把随机命中的单实例指标
当成集群聚合值。

双实例共享上传、输出和 OCR 缓存目录，日志分别写入 `data/logs/ocr-1` 与
`data/logs/ocr-2`。缓存文件使用原子替换保证写入完整，但两个实例同时收到相同的
首次图片时仍可能各执行一次推理；若这类请求很多，后续应使用 Redis 分布式锁。

**服务器参数**

当前默认：

```bash
OCR_CPU_THREADS=8
OCR_TEXT_RECOGNITION_BATCH_SIZE=6
OCR_MAX_CONCURRENT_REQUESTS=1
```

`OCR_CPU_THREADS` 建议不要超过服务器实际 CPU 核数。并发量较大时，优先部署多个容器实例进行负载均衡，不建议直接提高单个 Paddle pipeline 的并发数，否则 CPU 争抢后单次响应通常会更慢。

目前仍保留图片方向检测和预处理图片落盘。若调用方能保证图片方向正确，关闭 `OCR_USE_DOC_ORIENTATION` 还能进一步减少耗时；排查图片落盘约占几十到几百毫秒，考虑到你的倒查需求暂时没有关闭。

验证已通过：五类证件解析回归、Python 3.9 编译、Compose 生产/开发配置及真实营业执照识别。

**吞吐对照实验**

先关闭缓存启动双实例，否则重复图片会命中缓存，吞吐数据没有意义：

```bash
OCR_CACHE_ENABLED=false docker compose -f docker-compose.scale.yml up -d --build
python scripts/benchmark_http_throughput.py --url http://127.0.0.1:8001 --image test.jpg --document-type id_front --requests 8 --concurrency 2
python scripts/benchmark_http_throughput.py --url http://127.0.0.1:18081 --image test.jpg --document-type id_front --requests 8 --concurrency 2
```

第一条请求直连 `ocr-1`，代表单实例；第二条经过 Nginx，代表双实例。正式记录前先各
发一次请求完成模型预热。工具检测到 `X-OCR-Cache: HIT` 时会返回非零状态并提示
本次结果无效。

**OpenVINO 对照实验**

当前生产依赖保持 PaddlePaddle `3.1.1` 与 PaddleX `3.1.0` 不变。OpenVINO 通过
独立实验镜像安装 PaddleX HPIP、UltraInfer 和 Paddle2ONNX，ONNX 转换文件保存在
独立 Docker volume，不会写入生产 `models` 目录。构建并启动：

```bash
docker compose -f docker-compose.openvino.yml up -d --build
python scripts/benchmark_http_throughput.py --url http://127.0.0.1:8011 --image test.jpg --document-type id_front --requests 3 --concurrency 1
python scripts/benchmark_http_throughput.py --url http://127.0.0.1:8012 --image test.jpg --document-type id_front --requests 3 --concurrency 1
```

`8011` 是 Paddle/MKLDNN 基线，`8012` 是 OpenVINO。两者都强制关闭 OCR 缓存和
排查图片落盘。OpenVINO 首次启动会转换模型，耗时明显更长，应等待日志出现模型
初始化完成后再预热和计时。

也可在已安装 HPIP 的 Linux Python 环境直接运行质量与延迟对照：

```bash
python scripts/benchmark_ocr_backend.py --image test.jpg --document-type id_front --repeats 3 --warmup 1
```

报告会同时给出平均延迟、加速比、OCR 文本相似度以及结构化字段是否完全一致。

2026-08-02 本机 Docker 实测（缓存关闭、CPU 8 线程）：营业执照 Paddle/MKLDNN
平均 `1.916s`，OpenVINO 平均 `2.120s`，OpenVINO 慢约 `10.7%`；身份证反面
Paddle 平均 `0.3390s`，OpenVINO 平均 `0.3245s`，OpenVINO 快约 `4.3%`，但
P95 略差。两组结构化关键字段一致。当前收益不足以覆盖模型转换和镜像复杂度，生产
继续使用 `OCR_INFERENCE_BACKEND=paddle`，OpenVINO 保留为后续版本升级后的复测项。

同机双实例身份证反面实测（12 请求、并发 4、缓存关闭）：每实例 4 线程时，单实例
`3.148 req/s`，双实例 `3.651 req/s`，P95 从 `1.328s` 降到 `1.009s`。Nginx
upstream 必须配置共享 `zone`，否则多 worker 下最少连接状态不共享，会出现请求分配
失衡。
