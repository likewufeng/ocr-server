# OCR 性能与 CPU/GPU 选型汇报

汇报日期：2026-08-04

## 一、汇报结论

当前 OCR 服务的主要瓶颈是 CPU 推理计算，不是内存容量不足。

增加内存可以解决模型加载、多实例部署和 OOM 问题，但在内存已经足够的前提下，
不会显著降低单张图片的 OCR 推理耗时。当前 CPU 部署下，三类真实图片混合测试的
单请求无排队 P95 约为 `2.98 秒`；如果要求 50 个请求同时到达时仍保持接近这个
延迟，单纯增加内存没有效果，需要 GPU 或大量 CPU OCR 实例并行处理。

建议按业务目标选择：

- 如果允许 P95 `4-5 秒`，优先采用高频 CPU 加多实例，成本和改造风险较低。
- 如果必须单张图片和 50 并发都接近 `3 秒`，应建设 GPU 对照环境并进行真实图片压测。
- 不建议在没有压测验证前直接采购几十个 CPU OCR 实例。

## 二、当前实测结果

测试接口：

```text
http://192.168.28.177:18081/ocr
```

测试图片：身份证正面、身份证反面、营业执照。每轮 24 个请求，三张图片轮流发送，
每次请求使用唯一图片标记，避免 OCR 缓存命中。所有有效测试请求均成功，未出现接口
错误。

| 并发数 | 吞吐 | 整体 P95 | 结论 |
|---:|---:|---:|---|
| 1 | 0.753 req/s | 2.98 秒 | 无排队基线 |
| 2 | 0.708 req/s | 6.54 秒 | 开始排队 |
| 4 | 0.711 req/s | 7.73 秒 | 吞吐基本饱和 |
| 8 | 0.702 req/s | 14.98 秒 | 延迟明显增加 |
| 16 | 0.682 req/s | 28.31 秒 | 高延迟，不建议 |

单次预热请求中，身份证反面约 `1.16 秒`，身份证正面约 `1.34 秒`，营业执照约
`4.57 秒`。混合压测完成预热后，营业执照平均约 `2.93 秒`。营业执照、方向检测、
图像预处理和上传/落盘共同拉高了整体耗时。

## 三、为什么加内存不能解决 3 秒问题

一次 OCR 请求大致包含：

```text
上传图片 -> 保存原图 -> 图片方向检测 -> OCR 检测/识别 -> 结果解析 -> 保存结果
```

当前服务每个 OCR 实例配置 `OCR_MAX_CONCURRENT_REQUESTS=1`，并通过固定推理线程
执行模型。内存足够时，耗时主要由 CPU 执行检测模型、识别模型和预处理决定。

内存的作用主要是：

| 内存用途 | 作用 |
| --- | --- |
| 模型加载 | 防止服务启动失败或模型加载时 OOM |
| 多实例部署 | 每个实例都需要独立的 Python/PaddleX 运行内存 |
| 文件缓存 | 减少磁盘 I/O，但不会改变核心推理耗时 |
| 系统稳定性 | 避免内存不足导致交换，防止服务突然变慢 |

如果服务器已经有 64-128 GB 可用内存，再增加到 256 GB 通常不会让单实例从 3 秒
变成 1 秒；256 GB 主要是为了容纳大量 OCR 实例。

## 四、三种可选方案

### 方案 A：CPU 优化加多实例

适合允许 P95 `4-5 秒`，并发以突发为主的业务。

优化方向：

- 使用高主频、支持 AVX2 的独享 CPU。
- 保持 Paddle/MKLDNN，当前 OpenVINO 对营业执照测试反而慢约 10.7%。
- 调用方提前压缩超大图片，避免上传和预处理处理无效像素。
- 调用方能保证图片方向正确时传 `auto_orientation=false`。
- 不需要排查预处理图时关闭 `OCR_SAVE_PREPROCESSED_IMAGE`。
- 保持每个 OCR 实例 4 个 CPU 线程和单推理并发，使用多实例横向扩展。

参考配置：

```text
2 台服务器
每台 48-64 个专用 vCPU
每台 64-128 GB 内存
每台运行约 10-12 个 OCR 实例
```

参考预算：物理机约 `10-25 万元`，云服务器约 `1.5-4 万元/月`。

### 方案 B：CPU 集群硬顶 50 并发 P95 约 3 秒

当前每个实例只有一个独立 OCR 推理槽。50 个请求同时到达且不增加排队，理论上需要
约 50 个并行推理槽。

参考配置：

```text
52-56 个 OCR 实例
每实例 4 个 CPU 线程
208-224 个专用推理 vCPU
考虑系统余量后：256-288 个专用 vCPU
约 256 GB 以上可用内存
至少 10 Gbps 内网
```

推荐至少 4 台 `64 vCPU / 128 GB` 服务器，生产高可用建议 5 台。参考硬件预算约
`19-56 万元`，云服务器约 `3-10 万元/月`。

该方案成本高、运维复杂，而且严格保证 `2.98 秒` 几乎没有网络和系统抖动余量，
不建议直接作为第一采购方案。

### 方案 C：GPU 推理

GPU 更适合以下目标：

- 单张营业执照、发票需要更低延迟。
- 同时请求量较大，希望减少 CPU OCR 实例数量。
- 业务需要更稳定的 P95，而不是允许请求长时间排队。

GPU 不是只修改 `OCR_DEVICE=gpu:0` 就能使用，还需要：

- GPU 版 PaddlePaddle。
- CUDA、cuDNN 和对应驱动版本。
- 支持 GPU 的 Docker 基础镜像。
- 重新测试 OCR 模型、显存占用、批处理和并发数。

当前项目已经验证过 CPU OpenVINO，但营业执照场景没有获得收益；GPU 仍需用目标
服务器和这三类真实图片单独做对照实验，不能仅凭 GPU 型号估算最终 P95。

## 五、50 并发目标的选择建议

| 业务目标 | 推荐方向 | 预算级别 | 说明 |
| --- | --- | ---: | --- |
| P95 10-30 秒 | CPU 多实例 | 5-15 万元 | 成本最低，适合可排队业务 |
| P95 4-5 秒 | CPU 多实例优化 | 10-25 万元 | 推荐的 CPU 起步方案 |
| P95 约 3 秒 | GPU 评估或大型 CPU 集群 | 20-56 万元以上 | 需要专项压测确认 |
| 持续 50 QPS | GPU/大型集群/异步化 | 需专项报价 | 不等同于 50 个同时请求 |

## 六、最终建议

第一阶段不建议直接采购 4-5 台大型 CPU 服务器。建议先准备一台 `48-64 核/128 GB`
的测试服务器，或者租用同规格云主机，完成以下对照：

1. 当前 CPU mobile 模型基线。
2. CPU 优化后的图片尺寸、方向检测和预处理配置。
3. 一台 GPU 服务器上的同图片、同参数测试。
4. 分别测试单请求延迟、50 并发 P95、错误率、显存/内存和单位成本。

如果业务允许 P95 `4-5 秒`，优先选择 CPU 多实例，预计投入约 `10-25 万元`。
如果 `3 秒`是硬性 SLA，则建议先做 GPU PoC，再决定 GPU 集群规模；目前没有足够
实测依据承诺某一款 GPU 可以直接达到目标。
